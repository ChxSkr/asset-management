# 软件工程综合实践——项目方案

## 一、项目概述

### 1.1 项目名称

**数字资产管理系统（Digital Asset Management System）**

### 1.2 选题理由

数字资产管理系统（DAM）是针对企业和团队的数字文件（文档、图片、视频、音频等）进行集中存储、分类管理、版本控制和安全共享的平台。随着企业数字化转型的深入，数字资产管理成为刚需。本选题业务逻辑清晰、功能模块丰富，能够充分覆盖考核方案中的各项要求（15+核心界面、3+核心功能、E-R图设计、10+核心方法、20+测试用例等），且功能边界可控，适合在一周实训周期内完成核心功能的开发与文档编写。

### 1.3 团队配置

* **团队规模**：3人（符合考核方案"团队不超3人"要求）

* **角色分工**：

  * **组长（项目经理+后端开发）**：负责项目计划、概要设计、数据库设计、后端核心模块编码

  * **组员A（前端开发+UI设计）**：负责界面原型设计、前端编码、详细设计文档

  * **组员B（测试+文档）**：负责需求分析文档、测试文档、集成测试、文档整合排版

## 三、系统功能规划（≥3个核心功能）

### 3.1 核心功能模块

#### 模块一：用户管理与权限控制

* 系统管理员、普通用户两种角色

* 用户注册、登录、密码修改

* 基于角色的权限控制（RBAC）

* 个人资料管理

#### 模块二：数字资产上传与管理（核心模块）

* 资产上传（支持文档、图片、视频、音频等格式）

* 分类管理（树形分类结构，支持增删改查）

* 标签管理（支持多标签关联）

* 按分类、标签、文件类型组合筛选

* 搜索结果分页展示

#### 模块五：资产版本控制

* 同一资产支持上传新版本

* 版本历史记录查看

* 版本回退与下载指定版本

## 四、非功能需求（≥2种）

1. **安全性需求**：

   * 用户密码采用 BCrypt 加密存储

   * 使用 JWT Token 进行身份认证

   * 文件上传校验文件类型魔数，防止恶意文件上传

   * SQL注入防护（MyBatis参数化查询）

   * XSS攻击防护（前端输入过滤）

2. **性能需求**：

   * 普通查询响应时间 ≤ 2秒

   * 文件上传支持断点续传（大文件场景）

   * 支持至少50个并发用户同时访问

   * 资产列表分页加载时间 ≤ 2秒

## 五、数据库设计（E-R图）

### 5.1 核心实体

| 实体                      | 主要属性                                                         |
| ----------------------- | ------------------------------------------------------------ |
| **用户（User）**            | 用户ID、用户名、密码、角色、姓名、邮箱、电话、头像URL、创建时间                           |
| **资产（Asset）**           | 资产ID、资产名称、描述、文件类型、文件大小、存储路径、上传用户ID、分类ID、当前版本号、上传时间、更新时间、是否删除 |
| **分类（Category）**        | 分类ID、分类名称、父分类ID、排序号、创建时间                                     |
| **标签（Tag）**             | 标签ID、标签名称、创建时间                                               |
| **资产-标签关联（Asset\_Tag）** | 关联ID、资产ID、标签ID                                               |
| **资产版本（AssetVersion）**  | 版本ID、资产ID、版本号、文件大小、存储路径、上传用户ID、版本说明、上传时间                     |
| **下载记录（DownloadLog）**   | 记录ID、资产ID、下载用户ID、下载时间、IP地址                                   |
| **操作日志（OperationLog）**  | 日志ID、用户ID、操作类型、操作描述、操作时间、IP地址                                |

### 5.2 E-R关系描述

* 用户 1:N 资产（上传关系）

* 用户 1:N 下载记录（下载关系）

* 资产 N:1 分类（属于关系）

* 分类 1:N 分类（父子自关联，树形结构）

* 资产 N:M 标签（通过资产-标签关联表）

* 资产 1:N 资产版本（版本链）

* 用户 1:N 操作日志（操作记录）

* 用户 1:N 资产版本（版本上传关系）

### 6.2 模块划分原因

* **高内聚低耦合**：每个模块职责单一，资产管理是核心域，分类/标签/版本为支撑域，用户/系统为通用域

* **按业务领域划分**：遵循DDD（领域驱动设计）思想，模块边界与业务边界对齐

* **并发开发支持**：模块边界清晰，3名组员可并行开发不同模块

## 八、测试方案

### 8.1 测试策略（≥300字）

本系统的测试策略遵循软件工程V模型，从需求分析阶段开始同步设计测试用例，确保测试覆盖所有需求规格。测试分为四个层次：

**第一层：单元测试**。使用JUnit 5框架对后端Service层核心方法进行白盒测试，覆盖 uploadAsset()、softDeleteAsset()、buildCategoryTree()、searchAssets() 等关键业务逻辑，确保每个方法在正常输入、边界输入和异常输入下均能正确运行。单元测试覆盖率达到80%以上。

**第二层：集成测试**。使用Spring Boot Test框架对Controller层API接口进行测试，通过MockMvc模拟HTTP请求，验证请求参数校验、响应格式、异常处理等。重点测试用户登录认证流程、资产上传→查询→下载完整业务流程、版本上传→版本回退流程的端到端正确性。

**第三层：界面测试**。对照需求分析文档中的17个核心界面原型，逐页验证前端页面布局、交互逻辑、数据展示是否正确。使用手工测试方法，覆盖正常操作路径和异常操作路径（如空输入、超长输入、超大文件上传、非法文件类型上传等）。

**第四层：验收测试**。根据用户需求文档，设计验收测试场景，由团队内部交叉测试，模拟管理员和普通用户两种角色的真实使用场景，验证系统是否满足所有功能需求和非功能需求。最后进行回归测试，确保缺陷修复不引入新问题。

## 十一、风险分析与应对

| 风险                      | 影响     | 应对策略                       |
| ----------------------- | ------ | -------------------------- |
| 技术栈不熟悉（Vue/Spring Boot） | 开发进度延迟 | 提前学习基础教程，使用成熟的开源模板快速起步     |
| 文件存储方案复杂度               | 文件管理混乱 | 统一使用UUID命名存储文件，数据库记录映射关系   |
| 时间不足（仅1周）               | 交付质量下降 | 严格按里程碑推进，优先保证核心的资产管理CRUD功能 |
| 团队成员协作不畅                | 进度不一致  | 使用Git统一管理代码，每日同步，明确接口规范    |
| 大文件上传性能问题               | 用户体验差  | 前端分片上传 + 后端合并，设置合理的文件大小上限  |
